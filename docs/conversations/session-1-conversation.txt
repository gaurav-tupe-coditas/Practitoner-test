# SDD + EPIC workflow

Process matters as much as product. Specs come first, each file is confirmed by the user before the next starts, and implementation follows Explore, Plan, Implement, Commit.

## 0. Orient first (always)

1. Read `CLAUDE.md` if present, then check which of the files below already exist. Resume from what exists; never restart a stage that is done.
2. If the project has no SDD structure, propose it (section 1) and ask before creating anything.
3. If the project has its own `CLAUDE.md` rules, they override this skill where they conflict.

## Autopilot mode (on for Stessa work; off elsewhere unless the user turns it on)

The user set this on 2026-11-24 for work projects (Stessa), where deadlines no longer leave room for a gate on every file. In autopilot, Claude steers and the user steps in only for decisions that are hard to undo. This overrides the per-file gates and the "ask every question" rules below **for that project only**. Learning projects (Shardlands, Tessera, HMT) keep the full gates.

- **Take the recommended route** on every topic. Still write `analysis.md` and record each choice in `adr.md`, [masked]ed "Decided by Claude (autopilot)", so the reasoning can be read later during a bug hunt or an interview drill.
- **Move through the stages without stopping** for confirmation: requirements → spec → tests → plan → build, each file checked against the one before as usual.
- **Stop and ask only for one-way doors**: a choice that is expensive or impossible to reverse later. For example: database schema and migrations on shared data, public API or tool contracts other teams or clients will depend on, auth and security models (token handling, scopes, who can see what), anything that writes to external systems or prod, new dependencies or infra that lock the project in, data deletion or retention, and anything that contradicts a written requirement or a reviewer's earlier decision. Group these into one message: the decision, the recommendation, what it locks in, and what reversing it would cost.
- **Never skip the safety rules** in either mode: no env values in commits, no prod writes, project CLAUDE.md rules still win, commits only when the user asks.
- **End each stage with a short "what I decided and why" list** (one line per decision) so the user can skim it and veto anything before the build starts. Silence means go.
- **Feed the viva**: after a module lands, add its decisions and likely interview questions to the project's interview-drill notes, so the user can be quizzed on it later.

## 1. Project structure

```

## 2. Stages and gates

Order: `requirements` -> `specification` -> module split -> per module: `spec_task.md` + `analysis.md` -> `spec.md` -> `tests.md` -> `plan.md` + `tasks.md` -> implementation.

- **Do not start the next file until the user confirms the previous one.** Ask with a question that offers "Final, move on" as an option.
- `adr.md` is updated throughout, not at the end.
- Each stage's output is checked against the previous: spec cites requirements, tests cover every spec rule, tasks cover every test.

## 3. Working rules

- **Record every decision in the relevant document right after the user answers** (module `adr.md`, plus the spec text). Decisions that touch several modules also become a central ADR.
- If the user's answer is "other" or differs from the options, follow it. If it raises a risk (e.g. a hardcoded credential), state the risk in one line, offer a safer variant, and record whichever they choose. If they decline to answer a question, stop and wait; do not proceed on a guess.

### spec_task.md (the brief)
Goal, scope in/out, sources (doc sections), what it provides, what it depends on, a checklist of what `spec.md` must cover, a pointer to the open decisions in `analysis.md`, definition of done. The module session may extend it.

### analysis.md (the kick-off analysis, always, before any decision)
Every module starts with this. Write it into `analysis.md` and walk the user through it in the chat; never jump straight to bare seed questions. Read the code properly first (callers, consumers in other apps, deployment and migration conventions) so every claim is backed by a file#line link.

Open with a short "what the module must deliver" summary, then one section per decision topic. Each topic covers, in this order:
1. **What the requirement wants**: plain words, citing requirement and AC IDs.
2. **What we have today**: the current code, what it actually does (with file#line links), and any gap or bug it shows.
3. **Possible changes**: two to four options.
4. **Problems with each option**: risks, extra work, behaviour changes, who else has to change.
5. **Recommendation and why**.
6. **Consequence of the recommended change**: what behaves differently afterwards, for users, other modules and other developers.
7. **Impact analysis**: where the change lands (files and functions), how many places depend on it (callers, routes, tests, frontend consumers, other modules), and what the change itself depends on (other modules, other developers' work, infra or config).
8. **Question for the user**: the decision to make, with the recommended option first.

Close with an impact summary table (topic, files touched, dependents, depends on) and a list of things noticed that are out of scope but worth parking. After the user answers, record each decision in `adr.md` and [masked] the topic "Decided: ADR-..." in `analysis.md`.

### spec.md must cover
Fit to the module, but normally:
- Rules as enforceable statements (permissions, state machines, limits), each citing requirement IDs
- Data model and constraints (tables, keys, uniqueness, indexes, ownership)
- Flows and API endpoints with request/response shapes and error cases
- Events and audit entries emitted or consumed
- Ports exposed and used
- Non-functional points (limits, lifetimes, security, performance)
- Internal structure per the project's architecture ADR (files and what goes in each)
- Repository queries and transaction boundaries
- Constants (statuses, error codes with module prefix, event names)
- Contract requests, open questions, assumptions

### tests.md
Written only after `spec.md` is final. Map every spec rule to at least one test, with level (unit, integration, e2e), setup and expected result. Include negative and boundary cases and permission checks. State what is faked.

### plan.md and tasks.md
Written after `tests.md` is confirmed. `plan.md`: approach, order, risks. `tasks.md`: states phase and branch name, then phases of small tasks, each with a checkbox, the files touched, the tests it satisfies, and a done check. A task fits one commit.

## 5. Implementation (EPIC)

1. **Explore**: read the module spec, tests, and existing code before touching anything.
2. **Plan**: update `plan.md` before coding. Confirm if the plan changed materially.
3. **Implement**: go phase by phase through `tasks.md`. Tests first where the tests file allows. Tick tasks off as they pass. Check context between phases; summarise state in `plan.md` if it is getting long.
4. **Commit**: small commits per task or phase, **only when the user asks**. Follow any attribution rules from the harness. One worktree per module (section 5a).

Before a phase is called done: its tests pass, lint/boundary checks pass, and the module's contract tests against fakes pass.

## 5a. Parallel sessions and worktrees

One session, one module, one worktree. **Once per repo:** `git config pull.rebase true` and `git config rebase.autoStash true`, so a pull stashes, rebases and restores local edits instead of aborting. In VS Code also set `"git.autoStash": true`.

**Starting a module session:**

**While working:**
- Commit a dependency change (manifest plus lockfile) as its own small commit as soon as the user approves it. These files collide most often, with other sessions and with release bots that bump versions.

**Landing the work** (only when the user asks to commit or push):
- Trunk-based projects (all work on main): rebase onto `origin/main`, run the verify command, then `git push origin HEAD:main`. The worktree branch stays local.

**Cleanup:** once the work is on main, remove the worktree. Claude Code offers to on session exit; for plain git, `git worktree remove <path>` and `git branch -d <branch>`. `git worktree prune` clears stale entries.
