# Module ADRs: actiontrack

Central ADRs: `docs/adr/ADR-0001`, `ADR-0002`. Newest last.

### ADR-ACTIONTRACK-001: Duplicate items match on normalised text
- **Status:** Accepted
- **Date:** 2026-11-24
- **Decided by:** User (analysis T1, recommended option)
- **Context:** The same action repeats across meetings, sometimes with small wording changes (articles dropped, trailing due phrase added).
- **Decision:** Dedup key = (owner, owner_status, normalised task). Normalised = lower-case, punctuation removed, articles `a/an/the` removed, whitespace collapsed, trailing due phrase removed. No fuzzy matching.
- **Consequences:** Predictable and testable. Reworded repeats stay separate items.

### ADR-ACTIONTRACK-002: "next" and "end of" due phrases use the following calendar week
- **Status:** Accepted
- **Date:** 2026-11-24
- **Decided by:** User (analysis T2, recommended option)
- **Context:** Notes use `next Tuesday`, `end of next week`, `end of month`, and dates without a year.
- **Decision:** `next <weekday>` = that weekday in the following Monday-to-Sunday week. `end of next week` = Friday of the following week. `end of month` = last day of the meeting's month. A year-less date takes the meeting's year, rolling to the next year only if it would land more than 6 months before the meeting. `mid-<month>` and similar stay unresolved (effective due = meeting + 7 days, per requirements A-9).
- **Consequences:** `next Tuesday` said on Monday 2026-10-05 resolves to 2026-10-13. Some readers may mean 2026-10-06; this is a documented interpretation.

### ADR-ACTIONTRACK-003: Read `for` and trailing tomorrow/today/EOD as due phrases
- **Status:** Accepted
- **Date:** 2026-11-24
- **Decided by:** User (asked for the due-date misses to be fixed)
- **Context:** Sample notes say `schedule cutover for Saturday 10 Oct` and `circulate the summary tomorrow`; R12 left both undated, so they fell back to meeting + 7 days.
- **Decision:** Add `for` to the due keywords and accept a trailing `tomorrow`, `today` or `EOD` at the end of the line. A candidate must resolve completely to count, so `for 5 customers` or `for invoice rounding` stay undated. Requirements bumped to v1.1 (AC-4.4 only).
- **Consequences:** Two sample items get real dates. Small risk: `for Friday` in prose now reads as a due date.

### ADR-ACTIONTRACK-004: Launcher is one stdlib file calling the CLI in-process
- **Status:** Accepted
- **Date:** 2026-11-24
- **Decided by:** User (asked for a single run file that shows how to use the app)
- **Context:** Users should not need to learn argparse flags or manage paths.
- **Decision:** `run.py` at the repo root: menu when run without arguments, pass-through with arguments. It calls `cli.main` directly, keeps its data next to itself, and adds no dependency. `run.bat` and `run.sh` are two-line wrappers that find Python.
- **Consequences:** One entry point for non-technical users; the CLI stays the single source of behaviour, so the menu cannot drift from it.

### ADR-ACTIONTRACK-005: HTML reports are generated by stdlib, self-contained and escaped
- **Status:** Accepted
- **Date:** 2026-11-24
- **Decided by:** User (asked for an HTML view of results, in the app and in the docs)
- **Context:** Results are easier to read in a browser. Note text is untrusted input and could contain markup.
- **Decision:** Build HTML with string templates and `html.escape`; no template engine, no CDN, no external fonts. One shared `report.py` serves the app and the summary builder. The summary is regenerated from real runs, not hand-written, so it cannot drift from the code.
- **Consequences:** Zero new dependencies; works offline; the summary must be rebuilt (`python tools/build_summary.py`) after changes.

### ADR-ACTIONTRACK-006: The report refreshes after ingest, list and done
- **Status:** Accepted
- **Date:** 2026-11-24
- **Decided by:** User (wants the HTML created each time the command runs); command choice delegated to Claude
- **Context:** A report that must be asked for goes stale. Which commands should refresh it?
- **Decision:** Refresh after `ingest`, `done` (they change the data) and `list` (the view the user is looking at). Not `followup` (changes no items). Always the full item set. Opt out with `--no-report`; location with `--report`. Write failure is a warning, never a failed command.
- **Consequences:** `list` and `ingest` now write a file in the working directory (default `report.html`, git-ignored). Tests isolate the working directory so the repo is never written.

### ADR-ACTIONTRACK-007: Follow-up emails carry an HTML version built by hand
- **Status:** Accepted
- **Date:** 2026-11-24
- **Decided by:** User (recipients found the plain-text email ugly)
- **Context:** The Gmail create-draft tool accepts `body` (plain) and `htmlBody`. Email clients ignore `<style>` blocks and scripts inconsistently.
- **Decision:** Build the HTML in `draft.py` with inline styles and table layout, escaping every value; keep a tidy plain-text alternative. The `claude` sink passes both and says "draft only".
- **Consequences:** `Draft` gains an `html` field (default empty, so old callers work). Golden tests cover the plain text; a separate test covers structure and escaping of the HTML. Email-client rendering was checked by eye only.

### ADR-ACTIONTRACK-008: Sending is off by a master switch, and the app has no send path
- **Status:** Accepted
- **Date:** 2026-11-24
- **Decided by:** User ("it doesn't have to send"; a master switch in the env so we do not fail the requirements)
- **Context:** AC-8.4 forbids any send code path and T-28 tests that. A switch inside the app that enabled sending would break that.
- **Decision:** `ACTIONTRACK_ALLOW_SEND` (default 0) is a rule for the assistant, written in `CLAUDE.md` and `.env.example`; the app does not read it and cannot send. With the switch off the assistant creates drafts and the human sends them from Gmail, which is what the requirements describe.
- **Consequences:** The requirement stays true by construction. Emails that were actually sent went out through the Gmail connector outside the app, on explicit user instruction (see `GRADER.md`); the app itself never sends.
